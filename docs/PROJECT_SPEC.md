# Universal Interlinker — краткая спецификация проекта

Дата сверки: 2026-09-27.

## Цель

Сделать локальный сервис, который импортирует страницы сайта, находит подходящие внутренние ссылки, предлагает естественный анкор и контекст, показывает источник и цель и оставляет решение человеку. Начать с собственных сайтов как первых пользователей; позже подготовить перенос на VDS и развитие в SaaS для внешних пользователей.

## Принципы и границы

- Владелец сам регистрируется и добавляет сайты в интерфейсе.
- Импорт WordPress — только чтение через публичный REST API, включая опубликованные записи, страницы и открытые custom post types.
- URL цели всегда берётся из импортированного набора страниц сайта. LLM может проверять контекст и отказаться от ссылки, но не создавать адрес.
- Рекомендация требует ручной проверки. Принятие/отклонение фиксируется в локальном сервисе; публикация в WordPress пока не реализована.
- Не изменять пользовательские сайты и не подключать MySQL/использовать переданные учётные данные без отдельного явного запроса.
- Первые локальные результаты важнее широкой инфраструктуры; качество улучшать небольшими изменениями с тестами и измерениями.

## Что реализовано на дату сверки

- Локальный FastAPI-сервис запускается Docker Compose; проверка `GET /api/health` вернула `{"status":"ok"}`. Интерфейс доступен на `http://127.0.0.1:8000`; локальная почта для тестов — Mailpit на порту 8025.
- Регистрация по email и паролю, вход, сессии и разделение данных сайтов по аккаунтам. В локальном режиме подтверждение email не требуется; production требует подтверждения и настроенного SMTP.
- Пользователь добавляет сайт сам. Импорт WordPress читает posts/pages и публичные custom post types через REST API.
- Есть сканирование, выдача рекомендаций, фильтры, контекст с анкором, целевой URL, score и HTML-preview. Решение можно принять, отклонить или отложить; это не публикует изменения на сайте.
- Перед поиском рекомендаций можно выбрать минимальный score для выбранного сайта. Порог сохраняется в момент запуска без сброса прочих настроек. Во время задания показываются индикатор без выдуманного процента и фактически прошедшее время; после обновления страницы активное задание восстанавливается из БД.
- В URL интерфейса сайт образует первый сегмент (например, `/itpotokru/`), раздел — второй (`/obzor`, `/rekomendatsii` и т. п.); прямое открытие маршрута поддерживается.
- Для выбранного сайта можно загрузить CSV с поисковыми фразами и назначенными URL: интерфейс показывает пример строк и просит сопоставить колонки; данные хранятся в отдельной таблице проекта вместе с остальными полями выгрузки. Поддерживаются UTF-8 и Windows-1251, запятая/точка с запятой/табуляция; импорт ограничен 15 МБ и 100 000 строк. В базу проходят только URL того же домена. Вкладка «Ключевые фразы» показывает, найден ли назначенный URL среди импортированных страниц. Импорт запускает повторный поиск рекомендаций, когда в проекте есть минимум две страницы.
- Фраза из CSV может дать предложение с меткой `key`, только если она точно встречается в свободном тексте, соответствует теме импортированной целевой страницы и цель проходит семантическую и обычные защитные проверки. В карточке видны метка и сама CSV-фраза. Остальные предложения помечены «алгоритм». Этот механизм добавлен для ручной проверки на собственных сайтах; рост качества не измерен.
- Генератор исключает самоссылки и повторные цели, в том числе распространённые URL-варианты с `www`, HTTP/HTTPS и завершающим слэшем.
- Локально проверено: 51 Python-тест прошёл на 2026-09-27. Это не заявление о качестве рекомендаций на новых сайтах.

## Известные ограничения и наблюдения

- LSA — простой локальный baseline; MiniLM и Ollama доступны как опции. Контекстная проверка Ollama выключена по умолчанию. Рекомендации могут быть ошибочными, их нельзя публиковать автоматически.
- Наблюдалась сомнительная рекомендация из статьи «Переезд в Пензу» на страницу «Переезд в Пермь»: сохранённый фрагмент статьи о Пензе сам содержит раздел о Перми. Это две разные страницы, не самоссылка; предохранитель самоссылок её не удаляет. Пользователь может отклонить её в интерфейсе. Содержимое сайта не менялось.
- На локальном снимке `dagorod.ru` от 2026-09-27: 84 страницы, 4 945 импортированных строк CSV, 100 разных целевых URL. Первое включение точных совпадений ключевых фраз дало 6 предложений: 4 обычных и 2 с меткой `key`. Проверка показала, что оба `key`-анкора находились внутри `<h2>` больших вложенных HTML-блоков; этот вариант отклонён. После запрета ссылок в заголовках и повторного разбора сохранённых 84 HTML-снимков получилось 11 предложений, все от обычного алгоритма и все вне заголовков. Ключевые фразы остаются доступным источником, но по текущему снимку не проходят проверки для текстовых абзацев. Это проверка работы функции, не независимая оценка качества.
- Полный публичный SaaS ещё не готов: перед внешним развёртыванием нужны как минимум PostgreSQL и миграции, очередь фоновых задач, сброс пароля, надёжные резервные копии и проверка безопасности. Текущие детали запуска и переносов — в [`README.md`](../README.md) и [`docs/SAAS_ROADMAP.md`](SAAS_ROADMAP.md).

## Исследования качества

- В `local-data/cities/` находится локальный корпус 1150 статей Википедии о городах; это данные вне Git. Эксперимент оценивает только городские ссылки между статьями корпуса.
- Разбиение: 805 train / 172 dev / 173 test. Test нельзя использовать для выбора порогов или параметров.
- Исторические 703 совпадения из 968 рекомендаций на dev — результат настройки на dev, не независимая оценка. Поздняя реконструкция контроля дала отличающиеся метрики; причина расхождения не установлена. Не приписывать разницу новому алгоритму.
- Перед новым экспериментом проверить доступность артефактов и воспроизводимость контроля; сохранять конфигурацию, метрики, ошибки и проигравшие варианты. Не обещать рост качества до измерения.

## Ближайшие шаги

1. Улучшать качество на реальных импортированных страницах небольшими проверяемыми изменениями: диагностировать ложные рекомендации, добавлять адресные фильтры с регрессионными тестами и не скрывать допустимые переходы между разными статьями.
2. Собирать случаи принятия/отклонения и использовать их для оценки качества; не трактовать один пример или score как доказательство улучшения.
3. Для публичного SaaS сначала закрыть production-ограничения выше. Подключение и публикация на сайтах остаются под ручным контролем владельца.
